- Chat AI is split into `src/lib/ai/`: `modes.ts` (the four user modes + legacy id migration), `task-router.ts` (pure per-request classifier, tested), `models.server.ts` (inventory + per-mode candidates, max 3), `providers.server.ts` (endpoints/keys/timeouts), `prompts.server.ts`; `/api/chat` only orchestrates and reports the workflow via X-Vision-Execution/X-Vision-Output headers. Why: each part can fail or change independently and the router never alters the selected mode.
- User preferences live as validated JSON in D1 `user_settings.prefs` (`src/lib/settings.ts`); /api/chat reads them server-side, and Research web search runs in `src/lib/search/search.server.ts` (parallel providers, normalized + de-duplicated). Why: request bodies can't spoof preferences and each search source can fail alone.
- Research reports are stored in D1 `research_documents` (owner-only, server functions in `documents.functions.ts`, not in the generic query layer) and shown as a card linking to /documents/$docId; code output uses `components/chat/code-block` + `full-screen-code-view`. Why: documents stay permission-checked on the server and renderers stay reusable.
- Deep requests with a fixed number of separate deliverables run through `src/lib/ai/deep/engine.ts` (plan → one generation request per task → per-task deterministic + independent-model verification → targeted correction → cross-task final validation → ordered assembly), with state persisted per user+requestId in D1 `deep_executions` for resume and duplicate prevention, and real stages streamed as `vision_status` SSE events. Why: one request per deliverable is verifiable and correctable in isolation, and retries never redo accepted work.
- Deep Thinking Mode logic lives in `src/lib/ai/deep/` (pure, tested); /api/chat runs every other non-media deep request through the bounded pipeline: hidden plan (complex/long) → generate → deterministic validate → independent model review → correct → revalidate/re-review, logging stages as `[chat:deep]` JSON and disclosing any unrun or unresolved checks. Why: deterministic checks plus a separate review beat self-assessment, and loops stay bounded.

- Which workflow a chat message triggers (tool job, project, file export, or written answer) is decided only by pure `src/lib/ai/request-route.ts` (tested in `src/test/request-route.test.ts`); non-Default modes and long pasted briefs always get a written answer. Why: keyword triggers inside long prompts sent requests to the wrong workflow.
- Every provider call goes through `src/lib/ai/rate-limiter.ts` (per-provider RPM window, max concurrency, Retry-After cool-down, circuit breaker; tested) inside `streamFromProvider`, which logs `[ai:call]` telemetry. Why: one place enforces limits for chat, deep engine and jobs alike.

- Enterprise Login (VISION BDI): table `enterprise_attempts`, logic in `cloud/enterprise.server.ts`, domain checks in root `security/identity/domain-verification.ts`. Why: one place for attempt state and checks.
- Explicit instruction rules (word ranges, scripts per part, no-commentary, continuity) are parsed and checked in pure `src/lib/ai/deep/instructions.ts`, attached as optional `RequestAnalysis.instructions`, and fed into the existing validate/correct loop; issues carrying `items` trigger section-only rewrites spliced back, then full revalidation; outputs larger than `DEEP_LIMITS.batchItems` sections are generated, corrected and reviewed in bounded batches/windows with a continuity reference, structural repair is deterministic, and any unreviewed or unwritten part is disclosed. Why: one pipeline, same checks at every size, no hardcoded counts.
- Shared AI reliability helpers are pure in `src/lib/ai/`: `limits.ts` (all budgets), `failures.ts` (failure kinds, bounded jittered retry, safe user messages), `requirements.ts` (mandatory/optional requirement checklist with conflict/impossible marks; unchecked items never count as met), `context.ts` (budgeted history keeping standing instructions, task brief, untrusted-content fencing); tested in `src/test/ai-reliability.test.ts`. Why: one place for limits and honesty rules across chat, deep and jobs.
- Phase-2 reliability wiring: `streamFromProvider` wraps every model call in `withRetry` (failures.ts) so chat, Deep stages, Research and jobs share one bounded retry; Project Memory is enforced in /api/chat via `ai/memory.ts` + `memory.server.ts` (one D1 query for prefs+project; "project" scope adds same-project context and drops personal custom instructions); agent tools run only through `tools/tool-schema.ts` `executeTool` (schemas parsed from each tool's `params`), and tool model calls fence their input as untrusted; `startJob` returns the existing job for a replayed id (attempt 1). Why: helpers are only useful on the real paths.
- Chat requests are classified by `src/lib/ai/content-intent.ts` (deliverable / code / data / general) to add a format addendum; a single deliverable is wrapped server-side in one ````markdown fence (`copy-ready-stream.ts`), rendered by `components/chat/copy-ready-box` whose Copy writes clean text (+HTML); `text`/`prompt` fences stay literal. Why: one authoritative copy of each deliverable, no extra model call.
- Private files download via `src/lib/download.ts` (credentialed fetch → blob), never a bare `<a href download>` to an auth endpoint; `/api/artifacts/$artifactId` decides via pure `lib/jobs/artifact-download.ts` with distinct 401/403/404/410/502/500 codes. Why: browser download managers can drop the partitioned session cookie, which Chrome reports as "Needs authorization".
- Plugins: `plugins/manifest.ts` derives the 100 plugins from the format registry (code formats excluded — Coding Mode owns them) and `planPluginSend` decides each send (plugin = target, attachment = source); selections live in user_settings prefs.plugins. Repo analyzers keep one fetcher per provider in `repos/*.server.ts`. Why: the UI can never advertise a capability the registry lacks.
